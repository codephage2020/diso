深入浅出 · 示例

数据库索引：B+ 树

索引是一棵矮而宽的平衡树：每层只存区间界，查找沿树下降，用几次定点读取代替翻遍全表。

Part 1 · 先建立直觉

图书馆是怎么让你找到一本书的

想象一座没有目录的图书馆：一百万本书随便放。你要找其中一本，怎么办？

01 没有目录的时代

只能一架一架翻

书随便放，找哪本都得从第一个书架看到最后一个。藏书量翻倍，找书时间就翻倍，没有任何捷径。

02 目录卡片登场

先查卡片，再直奔书架

每张卡片只管一段字母区间，上面写着「L–S 的书在三楼 M 架」。你不用碰任何一本书，查卡片就能拿到位置。

03 导览分了好几级

大厅牌 → 楼层牌 → 书架

藏书太多，一层卡片装不下，于是目录也分级：大厅导览牌只说「去几楼」，楼层牌再说「去几架」，每级只做一次二选一。

04 书架彼此相邻

要一整段？顺着架子走

如果你要「25 到 60 之间的所有书」，查到起点那一架之后，直接顺着相邻的书架一路取过去，不用每本都回大厅重新查。

Part 2 · 拆开看真实机制

B+ 树：每个节点是一个磁盘页，每层一次定点读取

类比的图书馆到此为止。真实系统里，对应关系是这样的：

类比里的角色真实系统里是什么说明
书名 / 索书号索引键（key）被索引列的值，树按它排序
大厅 / 楼层导览牌内部节点只存键的分界值与子页指针，不存数据
书架上的书叶子节点存键 + 行指针（或整行，取决聚簇与否）
相邻书架叶子链表叶子间双向链接，范围查询顺序扫
一次走到书架一次磁盘页读取每节点 = 一个页（如 16KB），一层 = 一次 I/O

查找流程：从根节点读入内存，在页内二分找到键所属区间的子页指针，读入下一层，如此下降，直到叶子；叶子内再二分定位键，拿到行指针。树高通常只有 3–4 层，所以任意点查询只要 3–4 次磁盘读取。范围查询先定位左端点，再沿叶子链表顺序扫描。

再深一层：为什么 3 层就能装下一亿行

设每页 16KB，一个「键 + 指针」约 16 字节，则每个内部节点的扇出（fan-out）约为 1000。树能索引的行数随层数指数增长：

1 层（只有叶子）      ≈ 1,000 行
2 层                  ≈ 100 万行
3 层                  ≈ 10 亿行
4 层                  ≈ 1 万亿行

查找伪代码：

lookup(key):
    node = root
    while node 不是叶子:
        node = node.二分找到 key 所属区间的子页
    return node.叶子内二分定位(key)
Part 3 · 为什么这样设计

磁盘 I/O 是唯一要省的东西

3–4 次B+ 树点查的磁盘读取次数
100 万次全表扫描同一张表的读取量
≈1000单个 16KB 页的扇出（叉数）

磁盘比内存慢约十万倍，所以数据库结构的第一原则是「把树压矮」：扇出越大，层数越少，I/O 越少。二叉树在内存里是好结构，放到磁盘上就是灾难——B+ 树把每个节点撑到一整页，用一次读取换上千路分流。

得到

点查询从 O(n) 降到 O(log n)；范围查询沿叶子链表顺序扫，磁盘预读友好。

代价

每次写入都要同步维护索引：页满了要分裂，删除可能合并，随机写放大。

索引的本质，是用写入时的一点维护成本，预付读取时的全部检索成本。
Part 4 · 这个类比在哪里失效

图书馆的比喻有三处接不上

误解 1

「查索引也要从头翻目录」

真实的树每层只存区间界，页内二分、层间跳转，查找是对数级下降，不是线性翻卡片。之所以会这么想，是因为卡片柜在记忆里本身就是一个要顺序翻的抽屉。

误解 2

「索引越多越好，每列都建一个」

每个索引都是一棵独立维护的树：插入、更新、删除都要逐树同步。写多的表上乱加索引，写入会成倍变慢。类比里没有「改一本书要改 N 个卡片柜」的成本。

误解 3

「叶子存的就是整行数据」

只有聚簇索引（如 InnoDB 主键）的叶子存整行；二级索引叶子只存「键 + 主键值」，查到后还要回表再查一次。类比里「卡片直接告诉你书的内容」在这里不成立。

一句话总结

B+ 树索引用一棵矮而宽的平衡树，把磁盘读取从「翻遍全表」压成「3–4 次定点寻址」，代价是写入时同步维护这棵树。
